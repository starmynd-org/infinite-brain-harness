# Harness (Claude Code orientation)

This is the harness: the shared-parent tier of the Infinite Brain topology, and the folder you open in
Claude Code. It holds no work of its own. Its job is to route your work to the right brain, keep every
brain backed up and synced, and keep an inventory of every repo you run. Orient from this file first.
`AGENTS.md` is the Codex mirror; keep the two in sync.

## One folder for everything you own: `internal/`

`internal/` holds every repo your own operation owns and operates end to end. It carries two kinds of
child, and the difference is what the harness does with them, not where they sit:

| Kind | What it is | What the harness does |
|---|---|---|
| **A mounted brain** | Your shared work brain (a company brain, or a department brain that graduated to its own repo) and your individual brain (`individual-<your-name>/`) | Clones it in, validates it, registers it, syncs it, and copies its commands up so they work here |
| **Any other repo** | Product code, client-facing apps, tools: anything you own that is not a brain | Registers it and routes to it. Never mounts it, never copies its commands up |

The harness tells them apart **structurally, not from a list**: a child is a mounted brain when it
carries both `.claude/` and `_system/validate.sh`, the marker every brain built from the Infinite Brain
OS starter has and no app repo does. A hand-kept list would be wrong the first time a brain was added,
and the failure would be silent: the new brain's commands would simply never appear and nobody would be
told why. It also means an app repo can carry its own `.claude/` without leaking commands into this root,
which matters, because plenty of them do.

`external/` is the other half of the ownership axis: repos a client owns or that are co-operated with an
outside party, with one client's several repos grouped under `external/<group>/`. Brains are never
mounted from `external/`; a client's brain is theirs to mount in their own harness.

If `internal/` has no brains in it, this is a fresh machine: run `/start` and it clones them in.

## Routing rule (which brain gets the work)

1. **Default to the shared brain** for real, shared, or canon-reading work. Read its canon; never copy
   it into another brain, reference it by path.
2. **Individual brain for anything new, uncertain, or disruptive.** If the work might be wrong or could
   break what others rely on, it starts in your individual brain. Cheap to be wrong there.
3. **Proven individual work is promoted up, never edited into the shared brain directly.** `/sync`
   routes any core change to the shared brain onto a `proposal/<slug>-<topic>` branch for review.

Routing is by **domain, not by certainty.** Uncertainty is expressed by a node's `lifecycle_state`, not
by which brain it sits in. Work that belongs to the business and happens to be half-formed still belongs
in the shared brain, marked half-formed. Park work in the individual brain because it is *yours*, not
because it is *unfinished*: the other way round slowly turns a personal brain into a second, worse
company brain.

`.claude/CAPABILITIES.md` (regenerated by `/sync`) lists what each mounted brain holds, its tools,
workflows, agents, skills, and knowledge, with a one-line when-to-use, so you can direct work to the
right brain concretely rather than guessing.

## Commands

- `/start`: set up or wake up this machine. Establish git access (GitHub by default), create or clone
  every brain under `internal/` (on a fresh solo start it creates the private remotes too and re-points a
  starter clone's origin at the person's own repo), validate and register each brain, then run `/sync`.
  Run it first each day. If Claude ever seems lost, `/start` is the reset.
- `/sync`: back up your work and get the latest. Push your individual brain freely; push shared-brain
  content (outputs, sessions) to the shared branch; route shared-brain core changes to a
  `proposal/<slug>-<topic>` branch for review; pull the latest; refresh the copied command layer and the
  capability index from every mounted brain.
- `/save`: commit your work in every brain with your name on it, without pushing.
- `/promote-to-department`: package something from your individual brain for review.
- `/register-repo`: add one of your own repos to the registry.
- `/workspace-help`: explain all of this in plain words.

## How a brain's own commands work here, and how collisions are resolved

Claude Code loads only this root's `.claude/`, never a child repo's. So `/start` and `/sync` copy each
mounted brain's `.claude/{commands,skills,agents,rules}` up into this root, which is what makes a brain's
own tools work as slash commands from here.

Every brain here descends from the same starter, so on day one nearly every entity name exists in more
than one of them. A last-one-wins copy would silently hand you one brain's version of a name another also
carries, and two agents cannot register under one frontmatter name at all. So every collision is
resolved:

- a name only one brain carries keeps its plain name;
- a name several brains carry with **identical** content is copied once, plain;
- a name several brains carry with **different** content is copied once per brain under a tagged name
  (`co-<name>`, `me-<name>`), with no plain version, so you always know whose version ran.

The first time a name becomes tagged, two brains have started to diverge. That is expected, and `/sync`
says so out loud when it happens.

Two things to know: new copies load only after you **restart Claude Code**, and a copied command runs
against **its** brain, so change into that brain's folder first. `.claude/COPIED-FROM.md` maps every
copied entity back to its brain.

## The registry

Every child directory under `internal/`, `external/`, or an external group folder has exactly one entry
in `repo-registry/`, mounted brains included, so one inventory covers everything. `repo_kind` is `brain`,
`app`, or `mixed`; a brain also carries a `brain_tier` of `individual`, `department`, or `company`. An
app repo is an ordinary sibling with no brain ontology and no tier. `/start` writes the entry for each
brain it mounts; for anything else use `/register-repo` or follow `ADD-A-BRAIN.md`. An entry whose
directory is gone gets archived or deleted.

This harness provides children no backup. Each child's backup story is the `remote` field of its entry,
and `local-only` means none exists.

## What this harness never carries

No brain content of its own: no knowledge, doctrine, or entities authored here. No agents, skills, rules,
or workflows of its own beyond the commands above. No child repo state (commits, secrets, queues, build
artifacts), no live runtime state, no metrics or data. The children under `internal/` and `external/` are
independent git repos with their own remotes and history; this harness git-ignores their contents. The
copied command layer and the capability index are generated, git-ignored, and regenerated by `/sync`;
they are read-only downstream and never a second source of truth. No secret value lives here.

If a file answers a question about a brain's content, it belongs in that brain, not here.

## Style

No em dashes and no en dashes, anywhere, ever. Use commas, colons, or restructure the sentence.
